## 分布式缓存如何强一致（缓存和数据库，缓存的主从节点）*

强一致的核心是统一 leader、版本号和提交点。

写流程：

- 写请求统一路由到 leader。
- leader 对同一个 key 的写做串行化控制。
- leader 形成一条待提交的更新记录或版本 v2。
- leader 开启数据库事务写入 v2。
- leader 把这次更新同步复制到 follower。
- follower 写入成功后返回 ACK。
- leader 收到足够多 ACK，并且自身成功更新这个 key 为 v2 后，标记 v2 为 commit。
- leader 再向客户端返回写成功。

读流程：

- 读请求也统一路由到 leader。
- leader 返回最新 committed version 对应的值。
- 读写并发可以存在，但读不能看到未提交版本。

串行化控制：

- 可以用 per-key lock，写一个 key 时先拿这个 key 的锁，写完释放。
- 可以按分片做串行化。
- 也可以通过 leader 内部日志顺序保证同 key 写入顺序。

## goroutine 如何实现，goroutine 切换时保存哪些信息？

- Goroutine 是 Go 在用户态实现的轻量级协程。
- 每个 goroutine 维护自己的栈和状态。
- 切换时，Go 主要保存少量关键寄存器信息到 G 的 `gobuf` 结构体。
- 典型信息包括 `sp` 栈顶指针、`pc` 下一条指令地址、`ret` 系统调用返回值、`bp` 栈帧基址。
- 这些操作在用户态完成，开销远低于操作系统线程切换。

## goroutine 切换和线程、进程切换有什么区别？

- 进程和线程切换由操作系统内核完成，属于内核态切换。
- goroutine 切换由 Go runtime 完成，属于用户态切换。
- 进程切换最重，涉及虚拟地址空间切换，会影响 TLB 和缓存。
- 线程切换共享地址空间，但仍需要保存较多寄存器和调度状态。
- goroutine 切换更轻，不涉及地址空间变化，只保存少量核心上下文。

## UDP 不可靠体现在什么地方？

- 数据包可能丢失。
- 数据包可能乱序到达。
- 数据包可能重复。
- UDP 没有流量控制和拥塞控制。
- UDP 只负责尽力发送，不保证到达和顺序。
- UDP 仍然有 checksum 校验，数据损坏通常会被丢弃。

## UDP 的数据帧一般的大小是多少？太小或者太大的数据帧会怎么样？

- UDP 理论最大数据报大小约为 `65535 - 20(IP头) - 8(UDP头) = 65507` 字节。
- 以太网 MTU 通常是 1500 字节，因此 UDP payload 常控制在 `1500 - 20(IP头) - 8(UDP头) = 1472` 字节以内，避免 IP 分片。
- UDP 包太大会被 IP 层分片，一个分片丢失会导致整个数据报失效。
- UDP 包太小会让 header 占比变高，系统调用和网络包数量增加，带来 CPU 和网卡压力。
- 工程上通常控制 UDP 包大小，减少分片，同时兼顾传输效率。

TCP payload 常见最大值是 MSS，通常为 `1500 - 20(IP头) - 20(TCP头) = 1460` 字节。
